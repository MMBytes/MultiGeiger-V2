# Agent 10: architecture / design coherence

**Status: done**

## Design Review: MAX17048 Fuel-Gauge API Surface (V2.6.6)

**1. API surface coherence — this is a trap.** `fuel_gauge_ready()` and `fuel_gauge_present()` sit at the same call depth, take no arguments, return `bool`, and are named as a natural pair — nothing at the call site distinguishes "safe" from "unreliable." The disambiguating information lives entirely in a ~15-line file-header comment in `fuel_gauge.h` that a future engineer adding a 6th consumer (OTA-safety check, display icon, low-battery alert) has no structural reason to read before calling `fuel_gauge_present()` — it's the more semantically obvious choice for "should I treat this board as battery-powered," and IDE autocomplete will surface both names with equal weight. The current 3-vs-1 split (three call sites already use the unreliable one) is itself evidence the trap is real, not hypothetical — it already caught this codebase's own recent commits. A file-header caveat is not a fix; it's documentation of a known landmine that the type system does nothing to prevent stepping on.

**2. Layering — clean.** `fuel_gauge.c` stays a pure register-access + heuristic layer: I²C reads, unit conversion, VCELL hysteresis. No JSON, no HTML, no HA-schema knowledge appears in the driver. Conversely, the three consumers (`http_server.c`, `mqtt.c`, `mqtt_discovery.c`) contain no register-level assumptions — they only call the public API and format results. Layering is sound.

**3. Naming — `fuel_gauge_ready()` is a weak name and arguably worse than `present()` for a skimming reader.** "Ready" naturally reads as "ready to give you a real reading," which is *closer* to implying battery-truth than "present" does — the opposite of the intended distinction. The header comment has to do a lot of work to correct that first impression. `fuel_gauge_chip_detected()` (or `fuel_gauge_hw_present()`) would encode the actual invariant — chip ACK'd at init — directly in the symbol, with no comment required to avoid the wrong first guess. Recommend renaming at the next opportunity; it's a mechanical rename with a handful of call sites.

**4. Labeling consistency across the four surfaces — genuinely inconsistent, and this is a naming/trust problem independent of the gating-logic decision.** The log line hedges twice: gated on the honest signal (`ready()`) and labelled "Power supply/Battery" rather than "Battery." The other three surfaces both gate on the unreliable signal *and* use unhedged "Battery" language: `/status`'s `<h3>Battery</h3>`, MQTT's `batt_v`/`batt_soc`/`batt_rate` field names, and HA discovery's "Battery voltage" / "Battery" / "Battery charge rate" entity names — the last of these also claims HA's standard `battery` device class, which HA/end-users will render with a literal battery icon and percentage, the strongest possible claim of certainty in the whole system. So a user has no way to tell, from any of these three surfaces, that "Battery: 100%, charging" might just be a USB charger IC floating at 4.2V. That's a real end-user-facing trust gap, not just an internal code-comment gap — the log line's honesty fix didn't propagate to the surfaces regular users actually look at.

**5. Recommendation: (b) — do a small, scoped follow-up before this driver gets more consumers.** Two changes, both cheap: (i) rename `fuel_gauge_ready()` → `fuel_gauge_chip_detected()` (or similar) so the safe function's name carries its own warranty without requiring a header read; (ii) soften the three unhedged surfaces' *labels only* — e.g. `/status` heading → "Power supply/Battery", MQTT `batt_*` → acceptable as machine keys but HA discovery friendly names → "Power/Battery voltage" etc., matching the log line's already-established wording — without touching the gating logic the maintainer already scoped out this session. Both are small, mechanical, and close the gap between "what the driver author knows" and "what the next engineer or end user will assume."
